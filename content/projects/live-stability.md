## 1. CrashSight — 재현 어려운 라이브 크래시 추적

라이브 MMORPG에서 가장 까다로운 건 **재현이 어려운 비동기·플랫폼 한정 크래시**입니다. **CrashSight**로 수집된 콜스택을 분석해, 증상 대응에서 멈추지 않고 원인을 찾아 **구조적으로 차단**하는 것을 원칙으로 했습니다. 크래시 리포터는 맵 로드 전후 컨텍스트를 함께 남겨 콜스택만으로 상황을 좁힐 수 있게 했습니다.

```cpp
// Platform/CrashSightAdapter.h — 맵 로드 전후 컨텍스트와 함께 로그 수집
class FCrashSightAdapter : public TSharedFromThis<FCrashSightAdapter> {
    static void Log(ELogVerbosity::Type LogVerbosity, FString Message);
    void HandlePreLoadMap(const FWorldContext&, const FString& MapName);
    void HandlePostLoadMap(UWorld* World);
};
```

## 2. 비동기 / 레이스 컨디션 — 원인까지 추적한 사례

### ① 액터 풀링 × 비동기 로드 — freed-tick 크래시
- **증상** — 풀에서 다시 꺼낸 액터가 드물게 죽은 메모리 접근으로 크래시. 풀 재사용 타이밍과 비동기 로드 완료가 겹칠 때만 나타나 재현이 어려웠습니다.
- **원인** — 액터만 숨기고 컴포넌트 틱을 끄지 않아, Niagara `bAutoDestroy` 등으로 자기 파괴된 컴포넌트가 GC 후 freed 메모리 상태에서도 틱을 돌았습니다. 반납 전 걸려 있던 비동기 로드 핸들이 취소되지 않아 **뒤늦은 로드 완료 콜백이 죽은 컨텍스트를 건드리는** 경로도 있었습니다.
- **해결** — 풀 입출고 시 **모든 컴포넌트 틱까지 함께 토글**하고, 반납 시점에 진행 중이던 `FStreamableHandle`을 **취소**했습니다. 수명 경계마다 정리를 명시적으로 강제해 동일 유형을 구조적으로 차단했습니다. (풀링 구현 상세는 [최적화 페이지](/projects/optimization/) 참고)

### ② 별자리 룰렛 — 서버-클라 결과 불일치 (레이스 컨디션)
- **증상** — 룰렛 결과가 서버와 클라에서 **간헐적으로 다르게 표시**. 같은 조작을 반복해도 재현되지 않았습니다.
- **추적** — 결과에 관여하는 두 축(**WebSocket Notify 도착 시점** × **연출 상태 전이 시점**)에 로그를 심고 타임라인을 대조해, Notify가 연출 전이의 전/중/후 어디에 도착하느냐에 따라 결과가 갈리는 **순서 의존성**을 특정했습니다.
- **원인** — 클라가 결과를 **연출 상태 기준으로 확정**하고 있어, 네트워크 사정에 따라 도착 시점이 달라지는 Notify와 레이스가 생긴 구조였습니다.
- **해결** — 결과 확정을 **서버 Notify 단일 기준으로 일원화**하고 연출 전이 순서를 고정해, 순서 의존성 자체를 제거했습니다.

이 밖에 미니맵 좌표 NaN 방어, 순례 보상 정산, 장비 중복 착용/미장착 슬롯, 모바일 한정 크래시 등 다수의 현상·크래시를 회귀까지 추적해 핫픽스했습니다.

## 3. 아웃게임 — 퍼블리셔 대응 · 계정 운영

인게임 외에도 **아웃게임·퍼블리셔 대응** 영역을 담당했습니다.

- **해외 로그인 계정 차단** — 정책상 허용되지 않는 지역의 로그인 계정을 차단하는 처리
- **운영툴 기반 계정 잠금 대응** — 운영툴에서 내려오는 계정 잠금·제재 상태를 클라이언트에서 반영·대응
- **퍼블리셔 커뮤니케이션** — 퍼블리셔 요구사항을 클라이언트 동작으로 반영하고 이슈를 조율

## 4. 모바일 기기 대응

다양한 모바일 환경에서 안정적으로 동작하도록 **기기별 이슈**를 대응했습니다. 낮은 OS 버전이나 별도 그래픽 라이브러리를 쓰는 특정 기기에서만 나타나는 문제를 좁혀 대응해, 폭넓은 기기에서의 안정성을 높였습니다.
